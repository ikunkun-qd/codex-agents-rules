# Codex AGENTS.md 项目协作规则

> **面向个人 AI 编程协作的实战规则模板**：防遗忘、防脑补、防乱改、零污染。

这是一份可直接复用的 `AGENTS.md` 规范模板。它的核心目标是：**让 Codex、Claude、Antigravity 或其他编程 AI 在接手项目时先摸清现状、在跨会话迭代中精准断点续作、在排查故障与编码时严守底线，做到少猜、少漏、少乱改。**

本规则专门面向**个人与 AI 协作**场景：所有伴生文档默认保存在 `.agent-docs/` 目录中，作为 AI 的个人外脑、备忘录、契约与执行状态记录，不承担团队公开共享文档的职责，亦不对团队已有仓库产生任何侵入。

## 核心解决的痛点

1. **新会话失忆**：每次开启新会话 AI 丢失上下文，重复劳动或推翻先前决策。
2. **凭空虚构（幻觉）**：对接已有模块或外部接口时靠脑补虚构字段与业务规则。
3. **连环盲改与越权重构**：顺手格式化或修改无关代码，一个 Bug 未修好又引入新 Bug。
4. **设计与落地脱节**：只顾写代码导致架构失控，缺少可验证的验收依据。
5. **Git 仓库污染**：AI 擅自执行提交、强推，或盲目执行 `git add .` 将临时文件和未跟踪文件混入版本库。

## 核心设计理念

### 1. 本地隔离与零侵入（Zero-pollution，AI 全自动配置）
`.agent-docs/` 仅由开发者本人和本机 AI 维护。**AI 在首次创建个人文档前，会自动将 `.agent-docs/`、`AGENTS.md` 加入仓库本地的 `.git/info/exclude`**（或检测全局 Git 忽略）。**整个配置过程由 AI 自主静默执行，无需用户手动干预**；严禁修改项目原本的 `.gitignore` 和团队已有目录，零污染、不影响他人，即便在公司已有项目中也能安全落地。

### 2. 三重事实来源（Triple Sources of Truth）
AI 在判断项目现状时，必须遵循以下优先级与凭据划分，来源冲突时列出差异，严禁主观猜测：
- **目标行为（Should-be）**：已批准的 PRD、功能规格、API 契约、ADR 和数据字典。
- **当前实现（As-is）**：实际代码、配置文件、Schema、Migration、运行日志与测试结果。
- **执行进度（Progress）**：`PROJECT_STATUS.md` 与 Git 提交历史（计划文档仅代表目标步骤，不单独证明已完成）。

### 3. 断点续作优先级
新会话启动或继续未完成任务时，按既定优先级推进：
- **优先**：若 `Superpowers` 可用且存在唯一未完成实施计划，直接按 `subagent-driven-development` 推进。
- **回退**：若计划冲突、不可用或无需复杂计划，以 `PROJECT_STATUS.md` 中记录的 **“唯一下一步”** 与 Git 记录续作。

## 渐进式文档分级机制（核心亮点）

为了杜绝“过度文档化”，规则根据任务的影响范围实行动态分级。**默认从轻量档开始，绝不给简单改动增加负担**：

```
                 ▲
        完整级   │  涉及系统架构、公共API、数据模型、权限认证、重大生产依赖
      ┌──────────┴──────────┐  → 走 PRD → 规格 → 架构/契约 → 计划 → 编码/测试 → 验收 全链路
      │       标准级        │  影响单个模块的常规新功能
    ┌─┴─────────────────────┴─┐  → 简短功能设计 + 实施步骤 + 个人契约/字典同步
    │         轻量级          │  Bug 修复、文案/配置微调、不改接口/模型的小优化（默认档）
  ──┴─────────────────────────┴──  → 仅在 PROJECT_STATUS.md 登记任务与验证结果，不建多余文档
```

- **轻量级（默认档）**：日常 Bug 修复、文案调整、配置修改——仅在 `PROJECT_STATUS.md` 登记任务、根因和验证结果；若涉及接口/字段变化顺手在契约或数据字典补记，**不新建规格、计划和验收文档**。
- **标准级**：影响单个模块的普通需求——编写简要功能设计（目标、边界、验收标准）和实施记录后动代码；同步更新个人契约与数据字典。
- **完整级**：涉及架构调整、公共 API、数据模型、模块边界或生产依赖的重大变更——走全链路规范，重大决策设立独立 ADR。

## 端到端研发追踪与 Spike 试验

### 1. 标准开发全链路闭环
重大新功能与重要变更遵循端到端追溯链路：
$$\text{PRD} \longrightarrow \text{功能规格} \longrightarrow \text{架构设计与 API/数据契约} \longrightarrow \text{实施计划} \longrightarrow \text{代码/迁移与测试} \longrightarrow \text{验收记录}$$
每个模块、数据变更和测试用例均可反向追溯至对应规格或 PRD 条目。

### 2. 探索性试验（Spike / PoC）工作流
在技术方案、第三方库特性或数据结构尚不明确时，规则允许灵活探索：
1. **明确告知**：AI 明确告知用户正在进行“探索性试验（Spike/PoC）”；
2. **最小原型**：编写最小原型代码验证技术可行性；
3. **固化文档**：验证结论明确后，**必须先固化/更新相关规格、架构或契约文档，再推进正式编码与合并**。

## Agent 行为底线与交付基准

### “四不”行为准则
1. **不顺手重构**：严格遵循最小作用域原则，未经用户明确确认，不得顺手进行无关重构或大范围代码格式化。
2. **不虚构脑补**：严禁凭空虚构接口、字段、错误码、配置项或业务逻辑；对接他人接口直接读对方源码取证；无法确认的信息标注 `UNKNOWN` 向用户求证。
3. **不连环盲改**：严禁在未经验证的情况下连续堆叠修复补丁；每次修改后必须经过快速验证通过再继续下一步。
4. **不盲目暂存**：严禁未经确认直接执行 `git add .`！提交前必须先列出实际修改的文件清单供用户确认，经确认后精准暂存相应文件。

### 交付与验证三基准
- **分层覆盖**：前端改动必须执行页面/UI 呈现验证；后端与数据库改动必须执行自动化测试或真实链路调用验证。
- **结论可证伪**：完成结论必须基于当前会话实际跑通的验证结果；未经验证严禁声称完成；受环境限制未验证部分必须如实注明未覆盖范围与剩余风险。
- **规范化提交**：遵循 Conventional Commits 格式（`type(scope): subject`），AI 自动生成准确中文 message 并报告 commit hash；不擅自 push、amend、rebase 或使用 `--no-verify`。

## 个人文档体系架构（.agent-docs/ 速查）

`.agent-docs/` 为本机专属隐藏目录，按以下结构标准化归集，**仅在任务实际需要时创建对应文件，严禁为可选目录创建无意义空文件**：

```text
.agent-docs/
├─ README.md                         # 个人文档总索引、阅读顺序与目录约定
├─ prd/                              # 产品需求、用户场景、业务边界与验收目标
│  └─ PRD-<id>-<slug>.md
├─ specs/                            # 功能规格、详细设计与技术方案
│  └─ SPEC-<id>-<slug>.md
├─ architecture/                     # 架构总览、模块边界与依赖拓扑
│  ├─ ARCHITECTURE.md
│  └─ adr/                           # 架构决策记录（背景、原因、备选方案、影响与回滚）
│     └─ ADR-NNN-<title>.md
├─ api/                              # API/事件/共享类型契约、样例与集成备忘
│  └─ API_CONTRACT.md
├─ data/                             # 数据模型、字段业务语义、约束与迁移关联
│  ├─ DATA_DICTIONARY.md
│  └─ migrations/                    # 仅在项目约定将迁移文档归入 docs 时使用
├─ plans/                            # 实施计划、任务拆解与执行状态
│  └─ PLAN-<id>-<slug>.md
├─ project/                          # 跨会话状态记录与项目级索引
│  └─ PROJECT_STATUS.md
├─ testing/                          # 测试策略、测试矩阵与验收测试说明
│  └─ TEST_STRATEGY.md
├─ operations/                       # 部署、回滚、运行手册（Runbook）、监控与 SLO
│  ├─ DEPLOYMENT.md
│  ├─ RUNBOOK.md
│  └─ OBSERVABILITY.md
└─ acceptance/                       # 需求验收记录、实测证据与遗留风险
   └─ ACCEPTANCE-<id>-<slug>.md
```

### 核心状态文件：`PROJECT_STATUS.md`
跨会话的核心锚点，仅保留当前状态摘要与文档指针，不存大段历史：
- **必记要素**：当前分支/版本、需求来源、活动文档链接、当前任务；最近完成、进行中、阻塞项、**唯一下一步**（当前最优先的单个动作）；最近验证结果、关联 commit/PR/未提交变更、更新时间与负责人。

## 协同工具生态与降级保障

本规则与业界优秀 Agent 工具深度协同，并在环境受限时提供自动降级路径：

| 工具 / 机制 | 承担职责 | 降级与回退保障 |
| :--- | :--- | :--- |
| **Understand Anything** | 代码知识图谱生成、架构依赖分析与影响面评估（`$understand`, `$understand-chat`, `$understand-diff`） | 未安装时 AI 协助从 GitHub 安装；安装受限或失败时，自动回退为代码搜索、调用链排查、Git 历史与本地测试。 |
| **Superpowers** | 复杂任务拆解、子代理驱动开发（`subagent-driven-development`）与计划执行 | 未安装时 AI 协助安装；若工具不可用或计划冲突，自动改用 `PROJECT_STATUS.md` 的“唯一下一步”与 Git 记录续作。 |
| **Git Local Exclude** | 利用 `.git/info/exclude` 实现个人文档隔离，保护团队环境 | **AI 全自动接管**：首次创建个人文档前，AI 会自动将 `.agent-docs/`、`AGENTS.md` 写入本地排除文件，全程免人工干预。若新项目尚未初始化 Git（无 `.git/`），AI 先在本地记录，并在后续 `git init` 后第一时间主动补充写入，不阻塞任务。 |

## 快速上手指南

用户只需 **将规则放入根目录** 即可开始协作，繁琐的本地隔离与状态维护完全由 AI 自动接管：

### 1. 核心使用步骤（对用户而言只需 2 步）
1. **引入规则**：将 `AGENTS.md` 复制到项目根目录；
2. **开启协作**：像平时一样直接向 AI 提出需求（例如：“开始梳理需求”、“设计模块架构”或“排查某个 Bug”）。

### 2. AI 自动执行的幕后保障（免人工干预）
- **自动配置本地隔离**：AI 在首次创建个人文档前，会**自动将 `.agent-docs/`、`AGENTS.md` 写入仓库本地的 `.git/info/exclude`**（或检测全局 Git 忽略），**用户无需手动敲命令行配置**。若项目尚未执行 `git init`，AI 也会在后续初始化后第一时间主动补写，既不阻塞任务，又确保个人文档绝不误入版本库。
- **动态按需初始化文档**：
  - 小型脚本 / 原型 MVP：AI 仅创建单文件说明并维护 `PROJECT_STATUS.md`；
  - 正式生产级项目：AI 在编写业务代码前协助规划需求、架构设计与首期计划；
  - 日常小修改 / Bug 修复：自动走轻量档，仅登记进度与验证结果，不建多余文档。
- **团队/已有项目只读保护**：团队已有文档一律只读参考；AI 自动将个人备忘复制到 `.agent-docs/` 对应子目录维护，绝不破坏原有文件与团队 `.gitignore`。
- **公司与保密合规**：遵循企业安全制度，若有保密限制，AI 自动在个人文档中仅记录脱敏摘要和相对路径引用。

## 重要注意事项

1. **规则本身不替代代码**：知识图与规格文档用于导航与约束，真实的源代码、运行日志和测试结果永远是最高判定依据。
2. **状态文件保持精简**：`PROJECT_STATUS.md` 记录当前关键进展、阻塞与唯一下一步，完整历史交由 Git 和归档规格保存。
3. **临时资产及时清理**：调试过程中临时生成的脚本、测试数据文件，任务完成后务必清理；启动的 subAgent 任务完成时及时关闭。
4. **工具版本自适应**：外部工具命令名与参数以本机实际安装版本为准，不因工具参数差异中断核心开发任务。
